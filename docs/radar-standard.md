# Radar 記錄標準 — 每個追蹤項目必須可核實

> 建立：2026-11-16｜觸發：@Openclaw 指出 16 個追蹤項目中只有 1 個有法案編號，其餘 15 個無法核實
> 生效：即時，適用於 `radar/*.md` 與 `reports/*.md`

## 為什麼要有這條規則

2026-11-16 的實測顯示：全部 radar 與 reports 檔案掃描後，只找到 **3 個可核實編號**（R47558、R48642、HR10846），而其餘追蹤項目寫的是政策描述（「BIS 新規動向」「產地規則堵漏」）。

**沒有編號的「政策動向」不是事實，是待辦事項。** 它無法被核實，也無法被否證，所以它在 dashboard 上只是一個聲稱。

## 規則

**每個追蹤項目必須附上下列其中一種編號：**

| 類型 | 格式 | 例子 |
|---|---|---|
| 法案 | H.R. 編號 / S. 編號 | `H.R. 10846` |
| 聯邦公報 | FR 卷號 + 頁碼 | `91 FR 12345` |
| 行政命令 | EO 編號 | `EO 14105` |
| 已生效法律 | P.L. 編號 | `P.L. 117-167` |
| 訴訟/監管案卷 | docket 編號 | `docket EPA-HQ-2026-0123` |
| CRS 報告 | R 編號 | `R48642` |

**如果暫時找不到編號**，該行必須加上 `待補編號` 標記。這不是免責，是明確標示「這條未達到可核實標準」。

**如果只有單一二手來源**，必須加 `待證` 或 `待核`。

## 為什麼「號碼對、標題錯」是最危險的錯誤

2026-11-15 的實例：某模型給出 H.R.158 配「Chip Security Act」。H.R.158 確實存在，但它是 CLEAN Elections Act。《Chip Security Act》實際是 H.R.3447。

**這種錯誤無法靠「號碼存在」發現。** 它只能靠比對標題發現。所以：
- 引用法案時，**編號 + 標題 兩者都必須核實**
- 只有編號通過不算通過

## 工具

```bash
node scripts/id_gate.js          # 找出缺少編號的追蹤項目
node scripts/id_gate.js --json   # 機器可讀輸出
node scripts/id_gate.js --extract # 只列出所有已抽出的編號
```

Exit code 1 = 有缺口。這個檢查應該在每次 radar 更新後、commit 之前執行。

**注意**：`id_gate.js` 只檢查「追蹤項目」（有 `[ ]` 或「追蹤」標記的行），不檢查定義性描述。例如「EAR 是出口管理法」是參考資料，不是待核實的聲稱，不會被標記。

## Radar 輸出的寫法

**不好的寫法：**
```
- [ ] BIS 新規則 / Federal Register 公告
```

**好的寫法：**
```
- [ ] BIS 對華 AI 晶片新規 — 待補編號（須查 Federal Register，關鍵詞 semiconductor export control）
```

**最好的寫法：**
```
- [x] H.R. 3447 Chip Security Act — 已核實（Huizenga, R-MI；要求 BIS 對 AI 晶片加裝安全機制）
- [ ] 91 FR 12345（2026-07-26 生效）— 待核實頁碼
```

## 覆蓋率的現實

即使有這條規則，覆蓋率也不會是 100%。原因是：
- 有些政策方向根本還沒有法案（例如「H200 政策放收拉鋸」是行政裁量，沒有編號可引）
- 有些是預期性追蹤（「聽日追蹤點」），本來就未有编号

**這些應該明確標為 `待補編號` 或改寫成「觀察某官員言論」這類可核實的形式（附日期與來源）。**

真正的目標不是 100% 覆蓋，是**讓讀者一眼看出哪些條目已核實、哪些未核實**。
